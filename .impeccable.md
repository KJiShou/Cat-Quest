## Design Context

### Users and scope

Cat Quest serves Windows 10/11 desktop users managing tasks and focus sessions with a playful cat companion. The main application must make tasks, progress and actions easy to scan. The companion must remain glanceable while another application has the user's attention.

The global rules below apply to every project UI. Companion-specific requirements apply only to the companion window.

### Global visual authority

- The design language comes from `Assets/Packages/UI/Layer Lab/GUI Pro-SimpleCasual`. Before changing a UI, identify the closest exact source prefab/component and relevant package preview; record these references with the verification evidence.
- Reuse the existing project component when it already implements that pattern. Otherwise adapt a package component into a project-owned prefab or variant. Preserve vendor assets.
- Match the source component's hierarchy, rounded shapes, border/shadow treatment, spacing, icon proportions, typography and normal/selected/disabled states. Reusing one sprite or a similar color does not establish a match.
- Preserve established project typography, including current Fredoka usage, and intentional project adaptations. A style consistency task does not authorize replacing all fonts or undoing the user's styling.
- Keep the personality playful, friendly and calm. Use color and motion to explain actions and outcomes without overwhelming task content.

### Editable, reusable UI

- Existing scenes, prefabs, Inspector values and user edits are the starting point. Change only the requested component and necessary properties; preserve unrelated hierarchy, references, overrides and layout.
- Do not replace an existing page by deleting its children and regenerating it, or save a freshly generated root over an existing prefab. Static UI should remain serialized and editable; presenters bind state and events, while dynamic lists instantiate reusable item templates.
- Prefer the existing shared controls and feedback components before adding another implementation. Keep business rules, persistence and reward decisions out of visual components.
- A retained editor tool must make a targeted, repeatable change without resetting unrelated edits, and use Undo for interactive edits where applicable. Remove disposable construction scripts and their `.meta` files after their output is saved and verified, only after checking serialized references, code dependencies and ongoing authoring responsibilities. Retain useful verification tools.

### Feedback and visual acceptance

- Reuse `JuicyButton` for button feedback and existing outcome-specific feedback where appropriate. Verify hover, press/release, keyboard selection/submit and disabled behavior for changed controls.
- Meaningful actions need a clear success or error response after the authoritative result is known. Feedback may animate a value, selection or reward; it must not decide or duplicate the underlying operation.
- Keep hit areas and surrounding layout stable. Motion must settle and reset on interruption, page close, disable or focus loss; rapid repeated input must not accumulate scale, offset, callbacks or rewards.
- After every UI change, inspect fresh rendered screenshots beside the chosen source reference. Check hierarchy, spacing, typography, icon proportions, colors, shadows, clipping and interaction states. Inspect motion in Play Mode or a recording; a still image cannot verify juicy feedback.
- Use risk-tiered testing: local appearance edits need affected-state visual and interaction checks; shared controls, layouts or generators need representative dependent pages and edit-preservation checks; state, persistence or reward changes need the relevant behavioral regressions as well.
- Check ordinary application UI at 1920 x 1080 and 1280 x 720. Shared or responsive layout changes also need 1024 x 768 and 2560 x 1080, including expanded/collapsed sidebar states when relevant. Companion changes use its supported window sizes, including the minimum and live resizing.
- Report the reference used, fresh evidence inspected, checks run and any untested behavior. Historical screenshots or PASS files do not prove a later change is correct.

### Companion-specific direction

The supplied title-bar reference defines layout only; the user explicitly rejected a black bar. Keep a light SimpleCasual header, centered player name, the source-popup circular close control, a true rounded Windows region and UI mask, and the full game view below the header. Preserve established pin/minimize controls when changing another component.

1. Preserve the ninja training with Acorn. Animation fills the available content area; the timer on the sky is the only persistent content overlay.
2. Show one session action on the water. Session buttons fade in on pointer enter and fade out on exit at every supported size without changing the scene layout. Do not add unrelated information or hover tooltips.
3. Support four-edge and four-corner resizing with standard cursors; do not add a dedicated lower-right grip.
4. Keep window controls separate from session actions. Closing the companion does not stop Focus.
5. Preserve the authoritative main timer, state-driven animation and rewards. Keep the current End Early behavior; visual work must not change its session or reward semantics.
